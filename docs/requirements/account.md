# アカウント機能 要件定義書

## 1. 背景と目的

本アプリケーションには現在ユーザーという概念が存在せず、すべてのページが匿名かつ全員に共有された状態にある。
ページの所有・共有を実現するには、その土台となる「誰であるか」を識別する仕組みが必要になる。

本機能では、その第一歩としてログイン / ログアウトを実現し、アプリケーションがリクエストの主体を識別できる状態をつくる。
認可（誰がどのページを操作できるか）は本書の対象外とし、識別基盤を先に確立することを目的とする。

## 2. スコープ

### 2.1 対象

- サインアップ
- ログイン
- ログアウト
- ログイン中ユーザーの情報取得
- アカウント情報をアプリケーション DB に保持すること

### 2.2 対象外

| 項目                                     | 対象外とする理由                                                                       |
| ---------------------------------------- | -------------------------------------------------------------------------------------- |
| プロフィール編集（表示名・アバター画像） | 識別基盤の確立を優先するため。次フェーズで扱う                                         |
| メールアドレス / パスワードの変更        | 同上。                                                                                 |
| 退会（アカウント削除）                   | アプリ DB 側の関連データ削除方針が、ページの所有関係を決めてからでないと定まらないため |
| `pages` とユーザーの紐付け・認可         | 本機能完了後に別途要件定義する。                                                       |

## 3. 用語

- BFF
  - 本書では、ブラウザに渡せない資格情報（クライアントシークレット、アクセストークン、リフレッシュトークン）を代理で保持・行使する層を指す（10.3）

## 4. 前提と制約

- バックエンドは Rust + Axum + async-graphql で実装され、AWS Lambda 上で稼働する
- データベースは Neon (PostgreSQL)
- フロントエンドは Next.js 14 (Pages Router)
- 最小コスト構成を維持する。有料プランを前提とした選定はしない
- 既存の Cloudflare Worker は「ブラウザから Lambda を直接叩かせない」方針を取っており、`/graphql` へのリクエストはすべて Worker を経由する

### 4.1 フロントエンドにサーバーランタイムが存在しない

現状のフロントエンドは Next.js の静的エクスポート結果を Cloudflare の静的アセットとして配信する構成であり、API Routes も Middleware も動作しない。
したがって、**フロントエンド側でサーバーサイド処理を行う前提のライブラリは利用できない**。
認証ライブラリはこの制約を受けやすく、一般的な Next.js + 認証の実装例もほぼ API Routes を前提としているため、参照時は注意する。

## 5. 採用方針

6章以降の要件は、以下の選択を前提として記述する。
本章は決定の一覧であり、選定の根拠と却下した候補は10章に記す。

| #   | 論点                 | 決定                                         | 根拠 |
| --- | -------------------- | -------------------------------------------- | ---- |
| 1   | 認証の方式           | マネージド IDaaS を利用する                  | 10.1 |
| 2   | 利用する IDaaS       | Auth0                                        | 10.2 |
| 3   | 認証アーキテクチャ   | BFF パターン（トークンをブラウザに渡さない） | 10.3 |
| 4   | セッションの受け渡し | 署名付きトークンを HttpOnly Cookie に格納    | 10.3 |
| 5   | セッションの更新方式 | リフレッシュトークンによる自動更新           | 10.3 |
| 6   | ログイン画面の方式   | IDaaS がホストする画面へ遷移させる           | 10.4 |
| 7   | アカウントの作成契機 | 認証済みリクエストの初回受信時               | 8.2  |

### 5.1 この選択が要件に与える影響

要件と技術選定は一方通行では決まらない。
以下は選択の結果として要件側が従属している箇所であり、IDaaS を変更する場合は再検討が必要になる。

- 7.1 の `state` / PKCE
- 8.1 で `email` を UNIQUE にしない
  - Auth0 では、同じメールアドレスでもログイン手段が異なれば別のユーザーとして扱われる
- 6.5 セッションの継続
  - リフレッシュトークンが発行されることを前提としている
- MFA を要件に含めない
  - Auth0 の無料プランに含まれないため

## 6. 機能要件

### 6.1 サインアップ

**概要**:

SSIA
新規登録とログインを別の導線として提供することに意味があるのは、IDaaS のデータベース接続（メールアドレス + パスワード）を有効にする場合である。
ソーシャルログインのみを有効にする場合、両者に区別はなく、導線は 1 つで足りる（未決事項 2）。

**フロー**:

1. ユーザが新規登録を選択する
2. システムは IDaaS の登録画面へ遷移させる。
   このとき、IDaaS 側に既存のセッションが残っていても登録画面を表示させる
3. ユーザが IDaaS 上で新規登録を行い、認証を完了する
4. 以降は 6.2 のフロー 4 以降と同じ。
   ログイン中に開始した場合、確立したセッションは元のセッションを置き換える

**受け入れ条件**:

- [ ] アカウントを持たないユーザが、新規登録を意図した導線から IDaaS の登録画面に到達できる
- [ ] ログイン中のユーザも、同じ導線から新規登録を開始できる
- [ ] ログイン中に新規登録を開始したとき、IDaaS 側の既存セッションによって自動ログインされない
- [ ] 新規登録の完了後、新しいアカウントのログイン状態になる

**異常系**:

6.2 に準じる。

- ログイン中に開始して途中で離脱した
  - 元のセッションを維持したままアプリケーションに戻る

### 6.2 ログイン

**概要**:

SSIA

**フロー**:

1. ユーザがログインを選択する
2. システムは IDaaS のログイン画面へ遷移させる
3. ユーザが IDaaS 上で認証を完了する
4. システムはアプリケーションへ戻り、BFFがセッションを確立する
5. ユーザはログイン状態でアプリケーションを利用できる

**受け入れ条件**:

- [ ] 認証成功後、ログイン状態が画面上で判別できる
- [ ] セッションを保持する Cookie に `HttpOnly` / `Secure` / `SameSite=Lax` が付与されている
- [ ] ブラウザの JavaScript からアクセストークンを取得できない
- [ ] IDaaS 上の同一ユーザーは、常に同一のアカウントに対応する

**異常系**:

- ユーザが IDaaS の画面で認証を中断した
  - ログインしていない状態でアプリケーションに戻る。エラー画面は出さない
- 認証応答が改ざんされている（`state` 不一致）
  - セッションを確立せず、認証を失敗として扱う
- IDaaS が応答しない
  - ログインできない旨をユーザに伝える。未ログインでの閲覧は継続できる
- 同じコールバック（認可コード）が再送された
  - 2 つ目以降はセッションを確立しない。認可コードの使用は 1 回限りとする
- IDaaS がエラーを返した（同意の拒否、ソーシャル事業者側での失敗など）
  - セッションを確立せず、ログインできない旨をユーザに伝える。
    IDaaS が返したエラー内容をそのまま画面に出さない
- 認可コードとトークンの交換に失敗した（コードの期限切れ、通信断など）
  - 認証は完了しているがセッションは確立しない。
    ログインできない旨をユーザに伝え、やり直せるようにする
- 受け取ったトークンの検証に失敗した（署名・発行者・発行先・有効期限の不一致）
  - セッションを確立せず、認証を失敗として扱う（7.1）
- トークン検証に必要な公開鍵を取得できない
  - トークンを信頼せず、ログインを失敗として扱う。検証を省略して受け入れることはしない
- 認証は成功したが、アプリケーション側の処理が失敗した（DB 障害などで `accounts` を作成・取得できない）
  - セッションは確立できているため、再ログインを求めない。
    一時的な失敗として扱い、以降のリクエストで作成が再試行される（8.2）

### 6.3 ログアウト

**概要**: SSIA

**フロー**:

1. ユーザがログアウトを選択する
2. システムはセッションを破棄する
3. IDaaS 側のセッションも終了させる
4. 未ログイン状態でトップページに戻る

**受け入れ条件**:

- [ ] ログアウト後、セッション Cookie が削除されている
- [ ] ログアウト後に再度ログインを選択したとき、IDaaS の認証画面が表示される（自動で再ログインされない）
- [ ] ログアウト後、ログイン中ユーザーの情報が取得できない

**異常系**:

- 未ログインの状態でログアウトが要求された
  - エラーとせず、未ログイン状態でトップページに戻る
- ログアウトが連続して要求された
  - 2 回目以降も同じ結果になる（追加の副作用を持たない）
- IDaaS 側のセッション終了に失敗した
  - アプリケーション側のセッションは破棄したものとして扱い、未ログイン状態に戻す

### 6.4 ログイン中ユーザーの取得

**概要**:

クライアントが、現在ログインしているユーザの情報を取得できる。

**受け入れ条件**:

- [ ] ログイン中は、アカウントの表示名が取得できる
- [ ] 改ざんされたトークンや期限切れのトークンでは情報が取得できない

### 6.5 セッションの継続

**概要**: ユーザがログインした後、短時間で再ログインを求められることなく利用を継続できる。

**受け入れ条件**:

- [ ] アクセストークンの有効期限が切れても、ユーザの操作を中断させずに継続できる
